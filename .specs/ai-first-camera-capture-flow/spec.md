# AI-First Camera Capture Flow Spec

## Summary

Rework Garden Roof Deck camera capture so AI analysis happens before final plant assignment and save. The current flow proves camera capture, local photo persistence, and backend vision categorization, but it still asks the user to manually choose a plant before AI runs. The AI-first flow should capture an image, send it to the backend with the user's known plant inventory/context, receive ranked plant-match suggestions plus tags/insight, let the user confirm or correct the result, and then save the photo/observation/AI outputs to the confirmed plant.

Target flow:

```text
Take photo → AI identifies candidate plant + tags/insight → user confirms/corrects → save to confirmed plant
```

This spec builds on:

- `.specs/camera-photo-capture/`
- `.specs/ai-garden-agent-foundation/`
- `.specs/ai-photo-categorization-insights/`

## Product rationale

The product direction is AI-first. The camera should feel like a garden assistant, not a manual journal form with AI added afterward.

The current post-save categorization flow is useful plumbing, but it creates awkward UX:

- The user must choose “Save to Sungold” before the system has looked at the photo.
- AI tags/insights appear only after local save.
- If the selected plant is wrong, the AI output is attached to the wrong plant unless the user manually corrects later.
- The app cannot yet learn from “AI suggested X, user corrected to Y.”

AI-first capture should keep the user in control while making AI do the first pass.

## Goals

- Analyze captured photos before final save.
- Use OpenAI vision through the FastAPI + Agno backend, not direct mobile OpenAI calls.
- Send image plus known plant inventory/context to backend for plant matching and categorization.
- Return ranked plant candidates with confidence and rationale.
- Return tags, category, summary, and insight from the same analysis where practical.
- Let the user confirm, change, or fall back to manual plant selection before saving.
- Persist the confirmed plant assignment, AI suggestion metadata, AI tags, and AI insight locally.
- Preserve local-first photo storage: durable image remains on device; backend receives image transiently for analysis.
- Keep capture usable if backend/API/model fails.
- Keep web export and platform validation healthy.
- Make the flow efficient enough for real usage: one analysis call per capture attempt, cached result through confirmation/save.

## Non-goals

- No autonomous plant creation wizard in this slice, though the UX should leave room for “unknown/new plant candidate.”
- No cloud photo storage or sync.
- No changing plant records automatically without user confirmation.
- No deleting or overwriting existing photos.
- No background OS job queue.
- No multi-photo batch identification.
- No full botanical diagnosis or treatment plan. Short cautious insight only.
- No user-owned OpenAI key management UI.
- No public/Funnel exposure changes.

## Definitions

- **Capture candidate**: A photo captured in the camera flow but not yet persisted as a journal photo.
- **AI analysis**: Backend vision run over the captured image and compact app context.
- **Plant match candidate**: One possible existing plant the AI believes the image belongs to.
- **Confirmed plant**: The plant selected by the user before save. It may be the top AI suggestion or a manual correction.
- **AI-derived data**: Tags, insight, category, confidence, and match provenance generated by the backend.
- **System tags**: Existing deterministic tags like `camera` or plant name; not AI-derived.

## Existing behavior

Current camera flow:

1. User opens `/camera`.
2. User captures a photo.
3. App shows a result panel with selected plant.
4. User chooses plant manually.
5. App saves observation/photo/system tags locally.
6. App submits photo to backend best-effort.
7. Backend categorizes the saved photo.
8. Mobile persists AI tags/insight if response succeeds.

This spec changes steps 3-5 so AI analysis runs before save.

## Proposed user flow

### Happy path from camera tab

1. User opens camera.
2. User frames plant and taps shutter.
3. Captured image preview appears immediately.
4. UI enters `Analyzing photo…` state.
5. App submits captured image and context to backend pre-save analysis endpoint.
6. Backend returns:
   - ranked plant candidates,
   - tags,
   - category,
   - summary,
   - insight,
   - confidence/provenance.
7. UI shows suggested match:
   - `Looks like Sungold` or similar,
   - confidence label,
   - top tags/insight preview,
   - actions: `Save to Sungold`, `Choose another`, `Retake`.
8. User confirms suggested plant.
9. App saves locally:
   - observation row,
   - photo row,
   - system tags,
   - AI tags,
   - AI insight,
   - plant match provenance.
10. App navigates to Plant Detail for confirmed plant.
11. Timeline and Gallery show the photo and AI outputs.

### Happy path from Plant Detail

1. User taps `Log a new photo` from a plant page.
2. Camera opens with `plantId` route context.
3. User captures image.
4. Backend analysis receives the launched-from plant as a strong prior, not an automatic assignment.
5. If AI agrees, UI says e.g. `Looks like Sungold`.
6. If AI suggests another plant with stronger confidence, UI shows both:
   - `Suggested: Thai basil`
   - `Opened from: Sungold`
   - user must confirm one.
7. User saves to confirmed plant.

### Low-confidence path

1. Backend returns no confident plant match or confidence below threshold.
2. UI shows:
   - `I’m not sure which plant this is.`
   - useful AI tags/summary if available,
   - plant picker sorted by likely candidates and recent/contextual plants.
3. User chooses plant manually.
4. Save persists AI categorization plus `matchStatus = low_confidence_user_selected`.

### Backend unavailable path

1. Capture succeeds.
2. Analysis request fails or times out.
3. UI shows manual save fallback:
   - `AI is unavailable right now. Choose a plant to save locally.`
4. User chooses plant and saves.
5. Photo still persists locally.
6. Optional future retry is out of scope unless simple and safe.

### Retake path

- Retake discards the unsaved capture candidate and any transient AI result.
- Backend run history may remain for diagnostics, but no local journal rows are created.

## UX requirements

### Camera screen states

The camera route should have explicit states:

- `permissionLoading`
- `permissionDenied`
- `ready`
- `capturing`
- `capturedPreview`
- `analyzing`
- `analysisReady`
- `analysisFailed`
- `saving`
- `saveFailed`

Implementation may combine visual states, but logic should make these transitions clear.

### Copy guidelines

Replace misleading post-save copy.

Recommended copy examples:

- Before capture: `Frame the plant`.
- During analysis: `Checking your garden…` or `Identifying plant…`.
- Confident match: `Looks like Sungold`.
- Lower confidence: `This may be Sungold`.
- No match: `I’m not sure yet`.
- Confirm action: `Save to Sungold`.
- Correction action: `Choose another plant`.
- Fallback: `AI is unavailable. Save manually?`.

Avoid implying certainty beyond model confidence.

### Confidence display

Use plain language rather than raw percentages by default:

- `High confidence` for >= 0.80.
- `Possible match` for 0.55-0.79.
- `Not sure` below 0.55.

Raw confidence can be available in debug logs or developer UI, but not necessary in the main flow.

### Plant suggestion panel

Show:

- captured image preview,
- top suggested plant name,
- common/variety if available,
- confidence label,
- short rationale if backend provides one,
- 3-5 visual tags,
- one concise insight preview,
- confirm/correct/retake actions.

### Plant correction picker

When user taps `Choose another plant`:

- show active plants,
- rank top AI candidates first,
- include search/filter if easy,
- allow returning to suggested match,
- preserve analysis output when plant changes.

## Backend API

### Endpoint

Add a pre-save analysis endpoint:

```http
POST /agent/photo-identifications
Content-Type: multipart/form-data

fields:
- event: JSON string matching PhotoIdentificationRequest
- photo: image/jpeg or image/png file
```

When deployed behind platform routing, exposed as:

```http
POST /api/garden-roof-deck/agent/photo-identifications
```

In local Expo Go/dev direct backend mode, native may call:

```http
POST http://<tailnet-ip>:18100/agent/photo-identifications
```

### Request contract

```ts
type PhotoIdentificationRequest = {
  eventId: string;
  eventType: 'photo.identification_requested';
  occurredAt: string;
  launchedFromPlantId?: string | null;
  capture: {
    width?: number | null;
    height?: number | null;
    mimeType?: string | null;
    capturedOn: string;
  };
  context: {
    plants: PlantInventoryContext[];
    recentObservations?: RecentObservationContext[];
    recentAiInsights?: RecentAiInsightContext[];
    locations?: LocationContext[];
    app?: {
      schemaVersion?: number;
      platform?: 'ios' | 'android' | 'web';
      timezone?: string;
    };
  };
};
```

### Plant inventory context

Send compact plant inventory, not entire local database.

```ts
type PlantInventoryContext = {
  id: string;
  displayName: string;
  commonName: string;
  varietyName?: string | null;
  locationName?: string | null;
  statusKind?: string | null;
  statusLabel?: string | null;
  visualHints?: string[];
  recentTags?: string[];
  recentObservationNotes?: string[];
};
```

Include all active plants initially if the garden is small. If the list becomes large, limit to active plants plus likely/recent plants and add retrieval later.

### Response contract

```ts
type PhotoIdentificationResponse = {
  runId: string;
  status: 'succeeded' | 'failed' | 'skipped';
  providerConfigured: boolean;
  output?: PhotoIdentificationOutput | null;
  error?: string | null;
};

type PhotoIdentificationOutput = {
  summary: string;
  plantMatches: PlantMatchCandidate[];
  tags: AiTagOutput[];
  category: {
    label: PhotoCategoryLabel;
    confidence?: number | null;
  };
  insight?: {
    title?: string | null;
    body: string;
    kind: 'summary' | 'attention' | 'care_note' | 'tagging' | 'risk';
    confidence?: number | null;
  } | null;
  careRecommendation?: {
    title: string;
    body: string;
    confidence?: number | null;
  } | null;
  confidence?: number | null;
};

type PlantMatchCandidate = {
  plantId: string;
  displayName: string;
  commonName?: string | null;
  varietyName?: string | null;
  confidence: number;
  rationale?: string | null;
};

type AiTagOutput = {
  label: string;
  confidence?: number | null;
};
```

### Category labels

Reuse labels from categorization spec:

- `growth_update`
- `flowering`
- `fruiting`
- `harvest_ready`
- `watering_check`
- `pest_or_damage_watch`
- `health_check`
- `general_photo_log`

### Backend behavior

- Validate request and image content type.
- Run Agno/OpenAI with image plus compact plant inventory.
- Prompt should ask for ranked matches only among provided plants unless uncertain.
- Model must not invent new plant ids.
- If no confident match, return empty/low-confidence `plantMatches` and still return tags/summary if possible.
- Persist run metadata/output in `agent_runs`.
- Do not persist image bytes by default.
- Return output inline for v1.

### Backend prompt constraints

The agent instructions must include:

- You are matching this image to one of the provided plants when possible.
- Use only provided plant ids for `plantMatches`.
- If visual evidence is insufficient, say so via low confidence.
- Do not claim disease/pest certainty from one image.
- Keep insight short and actionable.
- Return structured output matching the schema.

## Mobile architecture

### New/updated services

Add a pre-save identification service, likely under `src/features/garden-agent/`:

```ts
GardenAgentService.identifyCapturedPhoto({
  localUri,
  width,
  height,
  mimeType,
  launchedFromPlantId,
}): Promise<PhotoIdentificationResult | null>
```

Responsibilities:

1. Load compact plant inventory/context from local repositories.
2. Build request payload.
3. Upload captured image to backend endpoint.
4. Validate response shape.
5. Return transient analysis result to camera UI.
6. Swallow or classify failures without crashing capture.

Do not persist AI outputs in this identify method. Persistence happens only after user confirms save.

### Camera save service

Update `CameraCaptureService.saveCapturedPhoto` to accept optional AI analysis:

```ts
saveCapturedPhoto({
  plantId,
  localUri,
  width,
  height,
  mimeType,
  aiAnalysis,
  matchProvenance,
}): Promise<{ observation; photo }>
```

It should:

- save observation/photo/system tags,
- persist AI tags from `aiAnalysis`,
- persist AI insight from `aiAnalysis`,
- persist match provenance if schema supports it,
- avoid re-calling the backend after save unless no pre-save analysis exists.

### Avoid duplicate AI calls

If pre-save analysis succeeded, do not call the existing post-save categorization endpoint again for the same capture. Reuse the analysis output.

If pre-save analysis failed and user saved manually, optional post-save categorization remains acceptable only if it does not block save and does not confuse the current flow. Recommendation: disable post-save AI for camera captures in this spec once pre-save path is active, except behind a retry/debug flag.

## Data model changes

### Photo tags

Continue using `photo_tags` for AI tags:

- `source = 'ai'`
- `confidence` from analysis result

### AI insights

Continue using `ai_insights` for photo insight:

- `scope = 'photo'`
- `kind` from analysis insight
- linked to plant/photo/observation after save
- `source_run_id = runId`

### Plant match provenance

Add one of the following.

Preferred table:

```sql
CREATE TABLE IF NOT EXISTS photo_plant_matches (
  id TEXT PRIMARY KEY,
  photo_id TEXT NOT NULL,
  observation_id TEXT,
  confirmed_plant_id TEXT NOT NULL,
  suggested_plant_id TEXT,
  source_run_id TEXT,
  match_source TEXT NOT NULL, -- ai_confirmed | ai_corrected | manual_fallback | launched_from_confirmed
  confidence REAL,
  rationale TEXT,
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL,
  deleted_at TEXT
);
```

Alternative if simpler:

- Add nullable columns to `photos`: `ai_suggested_plant_id`, `ai_match_confidence`, `ai_match_source`, `ai_source_run_id`.

Recommendation: use a separate table to avoid bloating photo records and to preserve future multiple-match history.

## Local persistence rules

When user confirms top AI suggestion:

- `confirmed_plant_id = suggested_plant_id`
- `match_source = ai_confirmed`

When user chooses a different plant:

- `confirmed_plant_id = user selected plant`
- `suggested_plant_id = top AI suggested plant if any`
- `match_source = ai_corrected`

When AI unavailable and user chooses manually:

- `suggested_plant_id = null`
- `match_source = manual_fallback`

When launched from plant and user confirms despite no/low AI:

- `match_source = launched_from_confirmed` or `manual_fallback` depending implementation simplicity.

## Error handling

### Analysis timeout

Set a user-friendly timeout target. Recommendation:

- show analysis spinner immediately,
- after ~8-12 seconds offer `Choose manually while AI keeps trying` only if implementation supports background completion,
- otherwise fail to manual selection with retry.

For v1, a simple request timeout and manual fallback is acceptable.

### Backend failed response

- Show fallback panel, not red screen.
- Keep captured image preview.
- Let user save manually.
- Do not create AI tags/insight.

### Invalid backend output

- Treat as analysis failed.
- Log for debugging.
- Save manually remains available.

### OpenAI unsafe/uncertain response

- If provider refuses or cannot identify, show low-confidence manual selection.
- Preserve useful non-sensitive tags only if output is valid.

## Privacy and retention

- Mobile local file remains durable source of truth.
- Backend receives the image for analysis only.
- Backend should not persist image bytes/base64.
- Backend run history may persist structured output, status, errors, provider/model metadata, and request metadata.
- Do not log API keys or image contents.
- Avoid storing full image payloads in logs, SQLite, or traces.

## Platform/dev environment notes

- Deployed platform path remains `/api/garden-roof-deck/`.
- Native Expo Go local testing may use direct backend origin like `http://100.109.137.10:18100`.
- Avoid hard-coding a single tailnet IP as a long-term solution; use env/config for `EXPO_PUBLIC_API_ORIGIN` or app-platform runtime config.
- Local backend dev should use writable `DATA_DIR=./data`; Docker/platform should use `/data` mounted to `/srv/runtime/garden-roof-deck/`.

## Web behavior

- Web `/camera` may stay unsupported/mock.
- Web build must still pass.
- Web should not try to use native file upload paths unless explicitly supported later.

## Observability/debugging

For development, make it easy to answer:

- Did the phone submit analysis?
- Did backend create a run?
- Did OpenAI/Agno succeed?
- What plant did AI suggest?
- Did mobile persist AI tags/insight?
- Was user confirmation AI-confirmed or corrected?

Recommended additions:

- backend `agent_runs` output visible via `GET /agent/runs/{runId}`,
- optional local console logs in dev only,
- store `source_run_id` on local AI insight/match provenance,
- optional debug text in camera result panel during Expo development.
